# AMEND — 게이트 반려에서 티켓 요구사항을 고치는 경로

게이트 반려에는 두 종류가 있다. **섞으면 안 된다.**

| 유형 | 뜻 | 가야 할 곳 |
|---|---|---|
| **(A) 산출물 품질 문제** | 계획이 부실하다 · 접근이 틀렸다 · 리뷰 지적이 맞다 · 커밋 메시지가 이상하다 | **해당 노드 재실행.** 티켓은 건드리지 않는다. (기존 동작) |
| **(B) 요구사항 불일치** | 티켓에 적힌 것이 사용자가 실제로 원하는 것과 다르다 | **AMEND.** 티켓을 고치고 N2 부터 다시 |

**애매하면 지어내지 말고 사용자에게 어느 쪽인지 물어라.** 잘못 분류하면
(A)를 (B)로 오인해 멀쩡한 티켓을 고치거나, (B)를 (A)로 오인해 틀린 요구사항 위에 계속 쌓게 된다.

## 1. 분류 신호

**(B) 쪽 신호** — 사용자가 *티켓의 내용*을 말하고 있다:
- "완료 조건에 X가 빠졌다" / "이건 완료 조건이 아니다"
- "이건 범위 밖이어야 한다" / "여기까지 해야 한다"
- "하위호환 유지해야 하는데 티켓에 없다"
- "티켓이 잘못 적혀 있다" / "대상 모듈이 틀렸다"

**(A) 쪽 신호** — 사용자가 *산출물*을 말하고 있다:
- "이 계획으로는 안 된다" / "이 방식 말고 저 방식으로"
- "테스트 목록이 부족하다" / "이 지적은 틀렸다"
- "커밋 메시지 다시"

요구사항은 그대로인데 접근만 다시 짜는 것이면 **(A)** 다.

## 2. 흐름

```
N3 ==GATE-PLAN==> [반려]
                     │
                     ├─ (A) → N3 재실행 (기존 동작)
                     │
                     └─ (B) → AMEND
                                ├ ge amend propose      원본 스냅샷 + 제안 본문 + 해시
                                ├ ge gate open --gate GATE-TICKET
                                ├ ← 사용자 approve 대기
                                ├ mcp__atlassian__editJiraIssue   (훅이 승인을 검사)
                                ├ ge amend applied      계획·승인 무효화
                                ├ ge retry --edge gate_to_amend   (상한 2회)
                                └ ge node N2 → N2 재실행 → N3 → …
```

GATE-REVIEW·GATE-COMMIT 반려에서도 같다. 다만 되돌아가는 거리가 멀어지므로
(이미 쓴 코드가 영향을 받는다) **무엇이 버려지는지 사용자에게 반드시 알린다.**

## 3. 강제 — 모델이 요구사항을 만들어낼 수 없다

`mcp__atlassian__editJiraIssue` 에 PreToolUse 훅(`ge-guard-jira.sh`)이 붙어 있다.

| 상황 | 결과 |
|---|---|
| `current_node` 가 `AMEND`/`N8`/`N9` 가 아님 | **차단.** 다른 노드는 티켓을 쓸 이유가 없다 |
| `N8`/`N9` | 통과 (완료 조건 체크박스·요약 댓글 — 기존 동작) |
| `AMEND` 인데 `ge amend propose` 를 안 함 | **차단.** 제안이 상태에 없다 |
| `AMEND` + 제안 있음, GATE-TICKET 미승인 | **차단** |
| 승인 후 제안 본문을 고침 | **차단** (해시 불일치) |
| 이미 반영된 제안으로 또 쓰려 함 | **차단** |
| `AMEND` + GATE-TICKET 승인 + 해시 일치 | 통과 |

승인은 **사용자가 채팅에 `approve` 를 입력할 때만** 기록된다(`hooks.md` §2).
모델도 오케스트레이터도 승인을 발화할 수 없다.

## 4. 요구사항이 바뀌면 계획은 무효다

`ge amend applied` 가 `plan` 을 비운다. GATE-PLAN 승인은 **계획 해시에 묶여** 있으므로
계획이 사라지면 그 승인도 자동으로 무효가 된다 — N4 로 다시 들어가려면 새 계획을 세우고
**다시 승인받아야 한다.** 훅이 물리적으로 강제한다.

이미 쓴 코드와 테스트는 지우지 않는다. 새 계획이 그것을 어떻게 살리거나 버릴지 정한다.

## 5. 무한 루프 방지

```bash
ge retry --edge gate_to_amend      # 상한 초과 시 exit 3 → node_status=escalated, 정지
```

기본 상한 **2회** (`config.json` 의 `retries.gate_to_amend`).
넘으면 그래프가 멈추고 사용자에게 넘긴다 — 그 시점의 진짜 문제는
"요구사항이 아직 확정되지 않았다" 는 것이지 더 고쳐서 될 일이 아니다.

## 6. 상태

```jsonc
"ticket_amendments": [
  {
    "seq": 1,
    "at": "2026-09-04T…",
    "from_gate": "GATE-PLAN",
    "reject_reason": "<사용자 반려 사유 원문>",
    "original_md": "<수정 전 티켓 본문 전체>",     // 롤백 근거
    "proposed_md": "<수정 후 티켓 본문 전체>",
    "proposed_hash": "sha256:…",                  // GATE-TICKET 승인이 여기 묶인다
    "code": "ab12cd",
    "applied_at": "2026-09-04T…",                 // null 이면 아직 반영 전
    "reentry_node": "N2"
  }
]
```

`original_md` 를 남기는 이유: 수정이 잘못됐을 때 사용자가 원본으로 되돌릴 수 있어야 한다.
N6 리뷰와 N9 요약은 이 원장을 읽고 **"이 티켓은 진행 중에 요구사항이 바뀌었다"** 를 드러낸다.
