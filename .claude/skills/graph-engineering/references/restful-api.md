# RESTful API 설계 규칙 (Spring Boot 전용, 강제)

`runtime.build.spring.boot == true` 면 이번 절 전체가 **항상 적용된다.** REST Docs 도입
여부와 무관하다 — 오히려 **REST Docs 스니펫이 곧 이 API 가 RESTful 하다는 증거**가 되어야 한다.
`document(...)` 로 남긴 명세가 URI·메서드·상태코드 규칙을 어기면, 그 문서는 "정확하지만
RESTful 하지 않은 API" 를 그대로 박제할 뿐이다. **구현과 문서 둘 다 이 규칙을 따라야 한다.**

## 1. 언제 적용되는가

컨트롤러(`is_controller_source` 판정 — `@RestController`/`@*Mapping`/`RouterFunction` 등)를
**새로 만들거나 엔드포인트를 추가·변경**할 때다. 기존 컨트롤러를 건드리지 않는 티켓에는
적용되지 않는다(새 위반을 만들지 않는 것으로 충분하다 — 무관한 리팩터를 강요하지 않는다).

기존 엔드포인트가 이미 이 규칙을 어기고 있고 이번 티켓이 그 엔드포인트를 **수정**한다면:
- 계약을 깨는 URI/메서드 변경은 하위호환 제약(`requirements.constraints`)에 걸릴 수 있다 —
  **임의로 뜯어고치지 말고** N3 계획에 문제를 명시하고 사용자에게 방향을 확인한다.
- 새로 추가하는 하위 리소스·필드는 이 규칙을 따른다.

## 2. URI 설계

- **명사·자원 중심, 복수형.** `/users`, `/orders/{orderId}/items`. 동사를 경로에 넣지 않는다.
  나쁨: `/getUser`, `/user/delete/{id}`, `/createOrder`. 좋음: `GET /users/{id}`, `DELETE /users/{id}`,
  `POST /orders`.
- **계층은 실제 소유 관계를 반영한다.** `/orders/{orderId}/items/{itemId}` — items 가 order 에
  종속될 때만. 독립적으로 조회 가능한 자원을 억지로 중첩시키지 않는다.
- **경로 변수는 식별자, 쿼리 파라미터는 필터·페이징·정렬.**
  `GET /users?status=active&page=0&size=20&sort=createdAt,desc` — 좋음.
  `GET /users/active` 처럼 상태를 경로에 넣지 않는다(그건 자원이 아니라 필터다).
- **행위가 자원·메서드 조합으로 표현 안 되는 경우만** 예외적으로 동사성 하위 자원을 쓴다.
  예: `POST /orders/{id}/cancel` (취소는 상태 전이이지 CRUD 가 아니다). 남용하지 않는다 —
  대부분의 "액션"은 사실 하위 리소스 생성/치환으로 표현된다.
- **케이스·네이밍은 저장소의 지배적 패턴**을 따른다(`conventions.naming`). 기존 API 가 없으면
  경로 세그먼트는 kebab-case, 필드는 프로젝트의 JSON 네이밍 정책(보통 camelCase)을 쓴다.

## 3. HTTP 메서드 — CRUD 의미와 정확히 일치시킨다

| 메서드 | 의미 | 안전(side-effect 없음) | 멱등 |
|---|---|---|---|
| GET | 조회 | O | O |
| POST | 생성(자식 자원) / 멱등하지 않은 액션 | X | X |
| PUT | 전체 치환(리소스를 통째로 덮어씀) | X | O |
| PATCH | 부분 수정 | X | 가능하면 O |
| DELETE | 삭제 | X | O |

- **GET 으로 상태를 바꾸지 않는다.** 조회 엔드포인트에 부수효과(카운터 증가 등)를 넣지 않는다.
- **PUT 은 리소스 전체를 받는다.** 일부 필드만 받는 "PUT" 은 사실 PATCH 다 — 이름을 맞춘다.
- **멱등성 계약을 지킨다.** 같은 PUT/DELETE 요청을 여러 번 보내도 결과 상태가 같아야 한다.
  구현이 이를 못 지키면(예: DELETE 재호출 시 500) 버그다.
- 기존 API 가 이미 다른 관례(예: POST 로 부분 수정)를 쓰고 있으면 **저장소의 지배적 패턴을
  우선**하되, N6 아키텍처 리뷰에서 지적하고 개선 여지를 남긴다(강제로 다시 쓰지 않는다).

## 4. 상태 코드 — 표준을 따르고, 전부 문서화한다

| 상황 | 코드 |
|---|---|
| 조회 성공 | 200 |
| 생성 성공 | 201 (+ `Location` 헤더로 생성된 리소스 URI) |
| 처리는 성공했지만 반환 바디 없음 | 204 |
| 요청 형식·검증 오류 | 400 |
| 인증 안 됨 | 401 |
| 인증은 됐지만 권한 없음 | 403 |
| 자원 없음 | 404 |
| 상태 충돌(중복 생성, 낙관적 락 등) | 409 |
| 의미상 처리 불가(검증은 통과했지만 비즈니스 규칙 위반) | 422 (프로젝트가 422 를 안 쓰면 400 으로 통일 — 컨벤션을 따른다) |
| 서버 오류 | 500 (의도적으로 노출하지 않는다 — 예외 처리 컨벤션을 따른다) |

- **완료 조건에 있는 에러 케이스는 전부 상태 코드와 함께 문서화한다**(§5, REST Docs 와 연결).
- 200/201 을 항상 반환하고 바디의 `success` 필드로 성공 여부를 표현하는 방식은 쓰지 않는다
  (HTTP 상태 코드가 곧 계약이어야 한다). 기존 코드베이스가 이미 그렇게 돼 있으면 새 엔드포인트로
  바로잡되, 기존 엔드포인트를 임의로 바꾸지 않는다(하위호환).

## 5. REST Docs 스니펫이 이 규칙을 증명하게 만든다

`document(...)` 를 쓸 때 다음을 **항상 함께** 기술한다 — 필드 설명만 있고 계약이 없는 문서는
불완전하다:

- 모든 케이스에서 **실제 HTTP 상태 코드**를 명시(`status().isOk`, `status().isCreated` 등) —
  스니펫에 상태 코드가 그대로 남는다.
- 경로 변수(`pathParameters`)와 쿼리 파라미터(`requestParameters`)를 구분해서 기술한다.
  쿼리로 가야 할 것을 경로에 넣은 채로 문서화하지 않는다 — 발견하면 설계를 먼저 고친다.
- 201 응답에는 `responseHeaders(headerWithName("Location")...)` 로 `Location` 헤더를 문서화한다.
- 완료 조건에 있는 4xx/5xx 케이스마다 **별도 스니펫**을 만든다(§4의 상태코드표에 맞춰).
- `document()` 식별자는 `<자원>-<행위>` 형태로 통일한다(`user-get`, `user-create`,
  `user-delete`, `order-cancel`). 파일마다 제멋대로 짓지 않는다.

이 결과로 나오는 문서 묶음이 곧 **이 API 의 RESTful 명세**다 — 자원·메서드·상태코드가 표로
읽히면 이 규칙을 지킨 것이고, 안 읽히면(예: 전부 200, 전부 POST) 위반이 곧 드러난다.

## 6. 강제 지점

| 노드 | 하는 일 |
|---|---|
| N3(`ge-planner`) | 새/변경 엔드포인트마다 자원·메서드·상태코드·URI 를 계획에 명시한다. |
| N4(`ge-tdd-developer`) | 컨트롤러를 이 규칙대로 구현하고, REST Docs 테스트에 §5 를 반영한다. |
| N6(`ge-review-architecture`) | 이 문서 기준으로 URI·메서드·상태코드 위반을 `blocking` 으로 판정한다. |
| N6(`ge-review-tests`) | 스니펫이 §5(상태코드·헤더·파라미터 구분)를 실제로 담고 있는지 본다. |

이 규칙은 `conventions` 와 달리 **저장소에서 추출하는 것이 아니라 이 문서가 기준**이다.
다만 기존 API 의 지배적 패턴과 정면충돌하면(예: 프로젝트 전체가 이미 다른 관례) N3 에서
사용자에게 확인한다 — 지어내지 않는다.
