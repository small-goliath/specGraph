# JIRA Ticket — 논의를 티켓으로

논의 중에 "이거 티켓으로 만들어줘" 를 받았을 때, **정해진 양식으로만** 티켓을 만든다.

이 양식은 Graph Engineering 의 N2a 파서가 소비하는 것과 **같은 양식**이다.
여기서 제대로 만든 티켓은 나중에 `/graph-run <TICKET>` 이 양식 위반으로 멈추지 않는다.

## 0. 절대 규칙

1. **양식 판정은 `jt` 가 한다.** "양식대로 썼습니다" 는 근거가 아니다.
   `jt validate` 를 통과하지 못하면 초안 등록 자체가 안 된다.
2. **생성은 사용자 승인 없이 불가능하다.** 승인 레코드는 사용자가 채팅에 직접 입력한
   `approve` 를 `UserPromptSubmit` 훅이 받아 기록할 때만 생긴다.
   `mcp__atlassian__createJiraIssue` 는 그 전까지 PreToolUse 훅이 **차단**한다.
   "승인받았다고 가정하고 생성" 은 존재하지 않는 경로다.
3. **요구사항을 지어내지 않는다.** 티켓에 들어가는 모든 문장의 근거는 **지금까지의 논의**다.
   논의에서 안 나온 완료 조건을 추측으로 채우지 마라 — 채웠다면 그렇게 밝혀라.
4. **모르는 것은 물어본다.** 특히 `완료 정의`(조사까지냐 배포까지냐)와 `제약`(하위호환·DB 스키마)은
   사용자만 아는 정보다. 임의로 정하지 말고 물어라.
5. **기존 티켓을 수정하지 않는다.** 이 스킬은 **생성 전용**이다.
   진행 중인 티켓의 요구사항을 고치는 것은 Graph Engineering 의 AMEND 노드 일이다.

## 1. 절차

### 1단계 — 논의에서 재료를 뽑는다

지금까지의 대화를 훑어 아래를 채운다. **대화에 없는 것은 비워두고 3단계에서 묻는다.**

| 섹션 | 어디서 나오는가 |
|---|---|
| 요약 | 논의의 핵심 한 줄. `[저장소] 무엇을 어떻게` |
| 대상 | 어느 저장소·모듈·진입점 이야기였나 |
| 배경 As-Is | 지금 무엇이 문제인지 **관측된 사실** |
| 배경 To-Be | 끝나면 무엇이 달라지는가 |
| 배경 왜 | 안 하면 무엇이 문제인가 |
| 완료 조건 | 논의에서 "이게 되면 된다" 고 한 것들 |
| 범위 밖 | 논의 중 "그건 이번에 안 한다" 고 한 것들 |
| 참고 | 대화에 나온 PR·이슈·로그·에러 메시지 |

저장소 사실을 확인해야 하면 코드베이스를 읽어라.
`graphify-out/` 이 있으면 `graphify` skill 을 우선 사용한다.

### 2단계 — 초안을 파일로 쓴다

```bash
JT=.claude/jira/bin/jt
$JT template                      # 빈 양식이 필요하면
```

초안은 **저장소 밖 임시 경로**에 쓴다(`.claude/jira/drafts/` 는 런타임 상태 디렉터리다).
스크래치패드가 있으면 거기에, 없으면 `/tmp` 에 쓴다.

작성 규칙 전문: **`references/template.md` 를 읽어라.** 요약하지 말고 그대로 따른다.

### 3단계 — 검증하고, 빈 곳은 사용자에게 묻는다

```bash
$JT validate --file <초안.md>      # 위반이 있으면 exit 2 + 무엇이 왜 문제인지 출력
```

- **위반이 나오면 고친다.** 다만 **논의에 근거가 없는 항목은 추측으로 채우지 말고
  사용자에게 물어라.** 특히:
  - `## 완료 정의` — 조사·보고까지인가, 배포까지인가?
  - `## 제약` — 하위호환 유지 필요한가? DB 스키마 변경 가능한가?
  - `## 범위 밖` — 이번에 안 할 것이 있는가? (없으면 `- 없음`)
- 경고(warning)는 차단하지 않지만 **사용자에게 그대로 보여준다.**

### 4단계 — 초안 등록 → 승인 요청

```bash
$JT draft --file <초안.md> --project PPS
```

검증을 다시 돌린 뒤 초안을 등록하고 **해시와 6자리 코드**를 준다.
그다음 사용자에게 제시할 것:

- **티켓 본문 전문** (요약 + 설명 + 요구사항 전체)
- 어느 프로젝트·이슈 타입으로 만들지
- **논의에 근거가 없어 추측하거나 사용자에게 확인받아 채운 항목**을 따로 표시
- 경고가 있으면 그 목록
- 마지막 줄:

> 이 티켓을 생성하시려면 `approve` (또는 `승인`) 를, 수정이 필요하면 `reject <사유>` 를 입력해 주세요. (code: `<코드>`)

**여기서 턴을 끝낸다.** 승인 신호를 보기 전에 티켓을 만들지 마라 — 훅이 막는다.

### 5단계 — 승인 후 생성

```bash
$JT check                          # 지금 만들어도 되는지 (exit 2 면 아직 안 된다)
$JT show --field summary           # 승인된 요약
$JT show --field description_md    # 승인된 설명 본문
```

생성 직전에 이슈 타입이 실제로 존재하는지 확인한다(프로젝트마다 이름이 다르다):

```
mcp__atlassian__getJiraProjectIssueTypesMetadata(cloudId, projectIdOrKey)
```

본문 형식은 `mcp__atlassian__getContentFormatGuide` 를 따른다. 그리고:

```
mcp__atlassian__createJiraIssue(
  cloudId, projectKey, issueTypeName,
  summary      = <jt show --field summary 그대로>,
  description  = <jt show --field description_md 그대로>
)
```

**승인된 본문 그대로 만든다.** 요약이 다르면 훅이 차단한다.

```bash
$JT created --key PPS-123          # 생성 결과 기록 + 초안 아카이브
```

## 2. 승인 신호 · 그래프와의 충돌

- 평소에는 채팅의 `approve`/`승인` 이 티켓 승인으로 기록된다.
- **Graph Engineering 게이트가 동시에 대기 중이면** 일반 승인어는 **그래프 몫**이다.
  그때 티켓을 승인하려면 사용자가 `/jira-approve` 를 입력해야 한다 — 훅이 그렇게 안내한다.
- `/jira-approve`, `/jira-reject <사유>` 는 언제나 티켓에만 적용된다.

## 3. 반려되면

사유를 반영해 초안을 고치고 `jt draft` 로 **다시 등록**한다(해시가 바뀌므로 재승인이 필요하다).
승인 후에 본문을 고쳐도 해시가 달라져 훅이 다시 막는다.

## 4. 상태 확인 · 정리

```bash
$JT status      # 초안 · 검증 · 승인 · 생성 현황
$JT show        # 전체 초안 JSON
$JT clear       # 초안 비우기 (생성된 티켓은 건드리지 않는다)
```

초안이 없으면 훅은 전부 즉시 통과한다 — 이 스킬을 쓰지 않는 작업에는 아무 영향이 없다.

## 5. 참조
